# Next Level 产品说明计划书

## 一、项目概述

### 项目名称

**Next Level**

### 一句话介绍

Next Level 是一个以 AI Agent 和 A2A 对话为核心，将求职匹配、岗位反馈与能力提升连接起来的智能求职招聘平台。

### 核心 Slogan

**投递有回音，努力有方向。**

### 项目定位

Next Level 面向求职者和招聘方，解决的不只是“有没有岗位”和“能不能投递”，而是双方是否真正理解彼此的需求，以及求职者在暂时不匹配时如何获得下一步。

平台由三个相互连接的部分组成：

1. **A2A 提效**：让求职者 Agent 与岗位 Agent 在求职广场中进行有限、多轮、可追溯的沟通。
2. **真实反馈**：把岗位要求、材料证据和对话结果连接起来，说明匹配依据与信息不足之处。
3. **能力提升**：当匹配没有发生时，把多个岗位反复出现的差距转化为具体的比赛、开源、项目和实践任务，并提供可追溯的知乎内容资源。

因此，Next Level 不是传统招聘流程上增加一个聊天机器人，而是把“寻找工作”和“变得更适合目标工作”放进同一条可执行路径中。

## 二、创作初心与问题发现

我做 Next Level，是因为我观察到，当前大量招聘平台仍然停留在文字列表、简历上传和人工投递：招聘方可能已经开始使用智能工具，求职者却仍然重复填写信息、等待回复，最后经常只得到一条没有解释的结果。

很多求职者并不是没有潜力，而是存在三种现实困难：

- 在学校学到的内容无法直接转化为岗位需要的证据；
- 有能力和想法，却缺少可以展示的经历、作品或量化结果；
- 收到拒绝或没有回应后，不知道差距在哪里，也不知道应该参加什么活动、做什么项目来补齐。

招聘方同样面临另一种困难：岗位描述很长，但真正影响判断的能力、证据和结果标准没有被说清楚；候选人的材料很多，却难以在有限时间内完成一致、可追溯的比较。

这造成了一个双向错配：一边有潜力却找不到机会，另一边有岗位却难以找到合适的人。传统平台主要优化“发布和投递”，很少真正帮助人提升达到目标岗位所需要的能力。

我的创作初衷，是做一个以人的能力提升为中心的求职平台：先让双方把需求聊清楚，再把反馈转化成可以执行的下一步。即使这次没有匹配成功，求职者也能知道自己缺少什么、如何补齐，以及下一次应该用什么新证据重新出发。

## 三、产品创作思路

### 1. 从“人找岗位”转向“Agent 先沟通”

在 AI 时代，求职者不应只是被动提交一份静态简历。求职者可以先用真实材料构建自己的 Agent，招聘方也可以用公司信息、岗位描述和附件构建岗位 Agent。

两个 Agent 先围绕岗位要求、工作场景、经历证据和结果标准进行有限对话，再把需要真人判断的部分交还给双方真人。

### 2. 从“没有通过”转向“知道为什么、下一步做什么”

匹配结果不能只显示一个分数。平台需要区分：

- 已经被证据支持的能力；
- 只有自述、但证据还不充分的能力；
- 岗位特有的能力差距；
- 多个岗位反复提出的共同要求；
- 不同岗位反馈之间的冲突。

这样，用户得到的不是一个简单排名，而是一张可以继续行动的路线图。

### 3. 用图文广场降低理解成本

传统招聘页面往往是密集的文字表格。Next Level 将岗位 Agent、求职者 Agent、成长活动和知乎求职经验组织成图文卡片与瀑布流，用户先通过图片、标签和摘要建立兴趣，再进入详情和对话。

底层的 Task、Message、Artifact、证据等级和状态事件默认收起，只在用户需要核对时展开，保证专业性与易用性同时存在。

### 4. 让知乎经验从“内容”进入“行动”

知乎上的求职经验、职业选择和实践分享不应只是被阅读一次的帖子。Next Level 将相关公开内容作为成长任务的参考资源：用户先看到自己在哪项能力上存在差距，再看到与该差距相关的知乎内容、比赛、开源项目或实践机会，并可以打开原始链接进一步了解。

## 四、核心用户流程

### 求职者流程

1. 使用知乎 OAuth 登录并选择求职者身份。
2. 上传或粘贴简历、项目材料和作品链接，支持 PDF、图片等材料预览。
3. 平台从材料中提取事实，同时保留原文证据片段，用户可以修改、确认或删除。
4. 用户进入 AI 模拟面试，围绕目标岗位进行文字或浏览器语音交互；语音转写必须经过用户确认。
5. 用户确认材料、面试摘要和披露范围后，生成求职者 Agent。
6. 用户将求职者 Agent 发布到求职广场，自主选择想了解的岗位、活动和知乎经验。
7. 用户逐项预览共享内容，并一次性授权选中的岗位，未授权的岗位不会被加入申请。
8. 求职者 Agent 与多个岗位 Agent 进行有限轮次的 A2A 对话。
9. 用户查看每个岗位的对话、反馈和结果，并在进阶路径中生成差距分析。
10. 平台聚合多个岗位的反馈，区分共同信号、岗位特有要求、证据问题和冲突反馈，生成 1 至 3 项可执行成长任务。

### 招聘方流程

1. 使用知乎 OAuth 登录并选择招聘方身份。
2. 上传公司介绍、岗位附件、公司详情链接，并补充岗位文字描述。
3. AI 只追问 3 至 5 个真正影响判断的问题。
4. 生成可编辑的岗位能力模型，包括能力名称、类型、描述、权重、硬性条件、证据标准和评估问题。
5. 权重合计通过 100% 校验后，招聘方确认并生成不可静默覆盖的 JobVersion 与岗位 Agent Card。
6. 招聘方发布岗位 Agent 到求职广场，招满后可以暂停新对话。
7. 招聘方在求职广场浏览求职者 Agent，查看其已确认的履历与作品摘要。
8. A2A 完成后，招聘方查看证据矩阵和 Agent 建议，再独立记录真人决定。
9. 真人可以选择邀约、暂不邀约或人工复核；如果覆盖 Agent 建议，必须填写覆盖理由。

## 五、产品功能设计

### 1. 求职广场

求职广场采用图文卡片和瀑布流形式，包含四类内容：

- **岗位 Agent**：展示岗位方向、薪资、地点、经验、福利、公司信息和岗位重点。
- **求职者 Agent**：展示求职方向、项目摘要、作品线索和可公开能力。
- **成长活动**：展示比赛、黑客松、开源项目和真实实践机会。
- **知乎经验**：展示求职相关公开内容，并附作者、摘要、链接、来源类型和获取时间。

用户点击卡片后进入详情弹层，在原有上下文中查看详情或开始 A2A 对话，不被突然带离当前页面。

### 2. A2A 对话

A2A 对话采用轮询式的有限交互：求职者 Agent 发送信息，岗位 Agent 回复并继续追问，双方在限定轮次内逐步补齐判断所需信息。

平台在数据模型和界面中保留：

- **Task**：一次独立的岗位沟通任务；
- **Message**：双方 Agent 的逐条消息和消息信封；
- **Artifact**：匹配结果、证据摘要或评估产物；
- **状态时间线**：任务创建、运行、完成、失败和人工复核等状态事件。

用户看到的是类似聊天记录的轻量界面，协议字段与原始载荷默认收起，需要审查时再展开。

### 3. 能力提升路径

成长路径不简单平均多个岗位分数，而是建立四类反馈结构：

1. 跨岗位重复信号；
2. 岗位特有要求；
3. 材料或作品的证据问题；
4. 不同 Agent 或真人之间的冲突反馈。

每项成长任务包含目标能力、产生原因、涉及岗位、原始反馈、学习内容、实践任务、推荐活动、预计投入、交付物、验收标准和复评方式。

平台重点推荐能产生新证据的黑客松、开源项目和真实实践，而不是只给出泛泛课程名称。

## 六、适配知乎社区的场景价值

### 1. 把知乎的经验内容连接到真实行动

知乎社区沉淀了大量关于求职、转行、面试、项目实践和职业选择的经验。Next Level 将这些内容放在用户已经明确的能力差距之后，让内容不再只是泛阅读，而是回答一个具体问题：

> 为了达到这个岗位要求，我现在应该补什么证据？有哪些真实经验可以参考？下一步可以做什么？

例如，用户在多个岗位反馈中反复缺少“可运行的 AI 产品作品”，平台可以将该差距与知乎相关经验、作品拆解和实践内容关联，并把它放入一项有交付物和验收标准的成长任务中。

### 2. 让社区内容具备可追溯来源

平台展示知乎内容时保留真实返回的标题、摘要、作者、链接、来源类型、获取时间以及实际返回的相关性或权威度信号。接口没有返回的字段不补写，不把模型生成的描述冒充作者原文。

用户可以从任务直接打开知乎原始内容，完成从“平台诊断”到“社区学习”的跳转。这样既尊重知乎内容来源，也让成长建议具备核验路径。

### 3. 形成“阅读—实践—再求职”的社区价值闭环

知乎内容帮助用户理解问题，比赛、开源和真实实践帮助用户形成新证据，新的证据再回到求职 Agent 和 A2A 对话中进行复评。

这个闭环让知乎社区的知识价值从一次阅读延伸到用户的真实行动，也让 Next Level 产生了区别于普通招聘产品的使用理由：用户来到平台不只是为了寻找机会，也为了更有能力地获得机会。

### 4. 降低进入社区和产品的身份成本

通过知乎 OAuth，用户可以使用已有知乎身份进入 Next Level，展示知乎授权返回的昵称、头像等基础资料，并按需读取公开创作与关注信息。

知乎 OAuth 只作为身份来源，岗位、简历、授权、A2A 和成长任务仍由 Next Level 自己管理。这样可以利用知乎的身份与内容生态，同时保持业务数据边界清晰。

### 5. 遵守社区内容与平台边界

Next Level 只在生成成长报告或用户主动刷新时调用知乎内容能力，不轮询、不在页面切换时重复请求。平台不使用知乎发布能力批量发帖、拉票或制造重复内容；推荐内容始终回链原始来源。

## 七、技术方案

### 1. 技术栈

- 前端与服务端：TypeScript、Next.js 16、React；
- 样式与交互：Tailwind CSS、统一的 App Shell、响应式布局；
- 数据校验：Zod Schema；
- 业务状态：确定性状态机和服务端 Store 边界；
- 外部能力：可替换的 LLM Provider、A2A Transport、知乎 Provider；
- 部署形态：开发环境可一键运行，生产环境可接入 PostgreSQL、对象存储和后台 Worker。

### 2. AI Provider

岗位结构化、追问生成、材料事实提取、面试问题、回答摘要、A2A 评估和简历润色统一通过 LLM Provider 调用。

Provider 支持 `live`、`mock` 和 `fallback` 三种模式：

- `live`：服务端通过环境变量调用真实模型；
- `mock`：无密钥时使用预置演示数据；
- `fallback`：模型超时或 Schema 校验失败后使用确定性安全结果。

模型输出必须经过 Zod Schema 校验，失败最多重试一次，仍失败时进入人工复核或 Demo Fallback。简历、岗位描述、知乎内容和 Agent 消息均按不可信输入处理，不能直接改变系统状态。

### 3. A2A 协议边界

平台保留内部 A2A Transport 适配边界，当前 MVP 使用可替换的进程内 JSON-RPC Transport，数据层按照 Task、Message、Artifact 和状态事件记录完整链路。

后续可以在不改动业务 UI 和领域模型的前提下，接入外部 A2A SDK 或远程 Transport。平台只声明已经验证的协议版本和兼容范围，不把内部实现描述为未经验证的完全官方兼容实现。

### 4. 知乎 Provider 与缓存

知乎能力由独立服务端 Provider 管理，按任务、规范化查询、Provider 和 Schema 版本生成缓存键。

- 默认缓存 TTL 为 24 小时，并可通过环境变量调整；
- 按用户、任务、应用和自然日记录调用计数；
- 支持每日预算、请求超时、最多一次重试和熔断；
- 明确区分 Live、Server Cache、Demo Cache 和 Offline Fallback；
- API 失败时展示缓存来源与获取时间；
- 只有生成成长报告或用户主动刷新时才调用，不轮询。

### 5. 数据与安全边界

生产版本中，每个登录用户需要有自己的 User、Role、CandidateProfile、EmployerProfile、JobVersion、Agent、Authorization、Application、A2ATask、Message、Artifact、Assessment、Decision、GrowthReport 和 ZhihuResource 数据范围。

知乎 OAuth Token、LLM API Key 和其他密钥只由服务端环境变量注入，不进入前端、URL、日志或 Git。平台不保存完整音频，不根据口音、音色、语速、停顿、性别、年龄或情绪推断能力。

## 八、演示与评审路径

评委无需理解协议细节，即可沿着以下路径完成体验：

1. 从营销页进入求职者空间；
2. 查看简历与 Agent、模拟面试和我的智能体；
3. 进入求职广场，在岗位 Agent 卡片中查看岗位详情；
4. 在原详情弹层内开始 A2A 对话，查看双方逐条消息；
5. 查看求职记录中的 Task、Artifact 和状态；
6. 进入进阶路径，生成差距分析；
7. 查看重复信号、岗位特有要求、证据问题与冲突反馈；
8. 打开成长任务中的知乎经验和活动链接，继续完成新的实践。

招聘方可以切换到招聘方空间，建立岗位 Agent、发布岗位、浏览求职者 Agent，并在我的智能体中展开查看 Agent 对话、证据矩阵和真人招聘决策。

## 九、项目创新点与差异化

### 1. 从单向投递变成双方 Agent 沟通

求职者不再只是向岗位提交材料，岗位也不再只是发布一段静态描述。双方 Agent 可以围绕真实要求进行有限对话，提高信息匹配效率。

### 2. 从匹配结果变成可解释反馈

平台保留证据、消息、产物和状态时间线，清楚区分 Agent 推断、材料证据和招聘方真人决定。

### 3. 从招聘平台变成能力提升平台

匹配失败不会结束流程。系统把差距转化为比赛、开源和实践任务，帮助用户获得下一次真正有用的新证据。

### 4. 知乎内容不只是展示，而是行动依据

平台把知乎公开经验与具体能力差距和成长任务连接起来，让社区知识直接参与用户的职业行动。

### 5. 前台轻量，后台可追溯

用户前台看到的是简洁的图文卡片、聊天记录和行动按钮；复杂的协议字段、证据链、版本、授权和来源信息按需展开，兼顾普通用户的理解成本与评审对可信度的要求。

## 十、当前 MVP 与后续计划

当前 MVP 已覆盖：

- 求职者与招聘方双角色空间；
- 简历、项目、作品和岗位材料输入；
- 求职者 Agent 与岗位 Agent 创建和管理；
- 求职广场图文瀑布流；
- 多轮 A2A Task、Message、Artifact 和状态时间线；
- 招聘方 Agent 建议与真人决策分离；
- 成长报告、差距分类、成长任务和知乎内容资源；
- 知乎 OAuth、公开内容 Provider、缓存和 Demo Fallback；
- 无密钥环境下的完整演示链路。

下一阶段重点是工程化而不是盲目扩展功能：

1. 将当前可替换 Store 迁移为按用户隔离的 PostgreSQL 数据访问层；
2. 将 A2A 进程内执行迁移为可恢复、可幂等的后台 Worker；
3. 在验证真实 Provider 后接入稳定的流式语音能力；
4. 完成真实知乎 OAuth、知乎 Provider 和生产环境的联调；
5. 建立更细的权限、审计、限流和数据保留策略。

## 十一、评审总结

Next Level 试图回答一个真实而普遍的问题：当求职者和岗位互相需要，却因为能力证据与需求表达不一致而错过时，平台能不能让双方先通过 Agent 把话说清楚，并在没有匹配成功时告诉求职者如何变得更接近目标。

知乎社区拥有丰富的经验内容、真实讨论和知识沉淀。Next Level 将这些内容与 A2A 反馈、岗位差距和可执行实践连接起来，让用户从阅读获得理解，从实践获得证据，再带着新的证据回到求职场景。

这就是 Next Level 的创作初心：**让投递不再只有等待，让反馈真正带人走向下一步。**
